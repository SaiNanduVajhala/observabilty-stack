# PromQL & LogQL In-Depth Guide

This guide breaks down every Prometheus Query Language (PromQL) and LogQL query implemented across our dashboards and alerting rules.

---

## 1. PromQL Fundamentals

Prometheus stores metrics as time-series data: a metric name, key-value labels, a timestamp, and a float64 value.

There are four primary metric types:
- **Counter**: Cumulative value that only goes up (e.g., total requests received).
- **Gauge**: Instantaneous value that goes up and down (e.g., memory usage, temperature).
- **Histogram**: Samples observations (typically durations or response sizes) and counts them in configurable buckets (`_bucket`), while also tracking count (`_count`) and sum (`_sum`).
- **Summary**: Similar to histogram, but calculates configurable quantiles client-side.

---

## 2. PromQL Queries Used in this Project

### A. Total Request Rate (R in RED)
```promql
sum(rate(http_requests_total{job="sample-app"}[1m]))
```
- `http_requests_total{job="sample-app"}`: Filters the raw counter time-series for the `sample-app` scrape target.
- `[1m]`: Range vector selector. Looks at observations across the past 60 seconds.
- `rate(...)`: Calculates the per-second average rate of increase of the counter over the range window. Handles counter resets automatically (e.g., when the app restarts).
- `sum(...)`: Aggregates rates across all dimensions (methods, endpoints, status codes) into a single overall throughput figure.

---

### B. Request Rate Broken Down by Endpoint
```promql
sum by (endpoint) (rate(http_requests_total{job="sample-app"}[1m]))
```
- `by (endpoint)`: Preserves the `endpoint` label while summing away other labels (like HTTP method and status code). This lets you see which endpoint receives the highest traffic.

---

### C. 5xx HTTP Error Rate Percentage (E in RED)
```promql
(sum(rate(http_requests_total{job="sample-app", status=~"5.."}[1m])) / sum(rate(http_requests_total{job="sample-app"}[1m]))) * 100
```
- `status=~"5.."`: Regex matcher that matches any 3-digit status code starting with 5 (e.g., 500, 502, 503).
- Numerator: Per-second rate of 5xx failure requests over the last 1 minute.
- Denominator: Total per-second request rate over the same window.
- `/ ... * 100`: Computes the failure percentage. If this exceeds 10%, our alert rule `HighErrorRate` triggers.

---

### D. P95 Latency Duration (D in RED)
```promql
histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket{job="sample-app"}[1m])) by (le))
```
- `http_request_duration_seconds_bucket`: Prometheus automatically generates bucket counters with an `le` ("less than or equal to") label for each histogram bucket (e.g., `le="0.1"`, `le="0.5"`, `le="+Inf"`).
- `rate(...[1m])`: Per-second rate of requests falling into each bucket.
- `sum(...) by (le)`: Groups the rates strictly by bucket boundary `le`.
- `histogram_quantile(0.95, ...)`: Computes the 95th percentile latency from the bucket distribution. It tells you: *"95% of users experienced a response time below this value."*

---

### E. Target Availability (TargetDown Alert)
```promql
up{job="sample-app"} == 0
```
- `up`: Built-in synthetic metric generated by Prometheus for every scrape target.
- `1`: Target scrape succeeded.
- `0`: Target unreachable or timed out.
- `== 0`: Evaluates to true when the target fails to respond.

## 3. LogQL Fundamentals (Grafana Loki)

LogQL is inspired by PromQL. A LogQL query consists of:
1. **Stream Selector**: Filters which log streams to inspect based on indexed labels (e.g., `{job="sample-app"}`).
2. **Pipeline Stages**: Parses, extracts, and filters log content (e.g., `| json`, `| status_code >= 500`).
3. **Metric Queries**: Aggregates log lines into time-series graphs (e.g., `count_over_time()`, `rate()`).

---

## 4. LogQL Queries Used in this Project

### A. Live Stream of Structured JSON Logs
```logql
{job=~"sample-app.*"} | json
```
- `{job=~"sample-app.*"}`: Selects logs shipped with matching job label.
- `| json`: Parses the log line as JSON and automatically extracts all top-level keys (`level`, `endpoint`, `status_code`, `duration_seconds`) as queryable fields without needing to reindex them in storage!

---

### B. Filter for Error Logs Only
```logql
{job=~"sample-app.*"} | json | level = "ERROR"
```
- Extracts JSON fields and only streams lines where the `level` property equals `"ERROR"`.

---

### C. Server Error Status Code Filter
```logql
{job=~"sample-app.*"} | json | status_code >= 500
```
- Numerically evaluates the parsed `status_code` field to display only internal server errors.

---

### D. Log Ingestion Volume Grouped by Log Level
```logql
sum by (level) (count_over_time({job=~"sample-app.*"} | json [1m]))
```
- `{job=~"sample-app.*"} | json`: Streams logs and parses the JSON.
- `[1m]`: 1-minute range window.
- `count_over_time(...[1m])`: Counts the number of log lines within every 1-minute window.
- `sum by (level)`: Groups log volume into separate series for `INFO`, `WARNING`, and `ERROR`. This visualizes log severity alongside metric spikes!
